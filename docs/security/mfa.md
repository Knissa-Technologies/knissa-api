# Multi-Factor Authentication (MFA)

## Overview

The Knissa API supports Multi-Factor Authentication (MFA) using
Time-Based One-Time Passwords (TOTP).

TOTP codes are generated by authenticator applications such as
Google Authenticator.

The MFA implementation is based on:

- `otplib`
- PostgreSQL
- Prisma
- Auth Tokens
- Session management
- Access Tokens
- Refresh Tokens

---

## Authentication Flow

When MFA is disabled:

```text
Email + Password
       ↓
Credential validation
       ↓
Session creation
       ↓
Access Token + Refresh Token
```


When MFA is enabled:

```text
Email + Password
       ↓
Credential validation
       ↓
MFA enabled
       ↓
MFA_LOGIN challenge
       ↓
TOTP verification
       ↓
Session creation
       ↓
Access Token + Refresh Token
```


The session and authentication tokens are only created after successful
MFA verification.

### Authentication Flow Overview

```text
                    LOGIN
                      │
              Email + Password
                      │
                      ▼
             Credential validation
                      │
                MFA enabled?
                 /         \
               NO           YES
               │             │
               ▼             ▼
       Session creation   MFA_LOGIN challenge
               │             │
               │             ▼
               │       TOTP verification
               │             │
               │             ▼
               └──────► Session creation
                            │
                            ▼
                 Access Token + Refresh Token
```

## MFA Components

The implementation is divided into three main operations:

```text
MfaService
├── enroll()
├── verifyCode()
└── verifyLoginCode()
```


### `enroll()`

Generates a new TOTP secret and the corresponding authenticator URI.

### `verifyCode()`

Validates the first TOTP code and activates MFA for the user.

### `verifyLoginCode()`

Validates the TOTP code during login when MFA is already enabled.

---

## TOTP Credential

MFA credentials are stored in the `mfa_credentials` table.

The credential contains:

```text
userId
secret
enabled
verifiedAt
```

The TOTP secret is sensitive authentication material and must never be
committed to source control or exposed through logs.

---

# MFA Enrollment

The enrollment process consists of two steps.

```text
Initialize MFA
      ↓
Generate TOTP secret
      ↓
Register secret in authenticator
      ↓
Verify six-digit code
      ↓
Enable MFA
```

After successful verification:

```text
enabled = true
verifiedAt = current timestamp
```

---

# MFA Login

When the user's MFA credential is enabled, the normal login process
becomes a two-step authentication flow.

## Step 1 — Password

The user sends their email and password to the login endpoint.

If the credentials are valid and MFA is enabled, the API creates a
temporary `MFA_LOGIN` challenge.

The API does not create an authenticated session at this stage.

---

## Step 2 — TOTP

The user sends:

- the MFA challenge token;
- the current six-digit TOTP code.

The API validates the challenge and then verifies the TOTP code.

Only after successful verification is the authenticated session created.

---

# MFA Login Challenge

MFA login challenges use the existing `AuthToken` infrastructure.

The token type is:

```text
MFA_LOGIN
```

Each challenge has:

- a five-minute lifetime;
- a single-use restriction;
- a user association;
- a hashed value stored in the database.

The raw challenge token is returned to the client, while the database
stores only its hash.

---

## Challenge Lifecycle

```text
Challenge created
       ↓
Valid for 5 minutes
       ↓
TOTP verification
       ↓
Successful?
   ┌───┴───┐
  YES      NO
   ↓        ↓
usedAt    rejected
   ↓
Session created
```

---

# Challenge Security

## Single Use

After successful MFA verification, the challenge is marked as used.

Attempting to reuse the same challenge must fail.

Expected response:

```json
{
  "success": false,
  "message": "MFA challenge has already been used."
}
```

## Expiration

MFA challenges expire after five minutes.

An expired challenge is rejected.

Expected response:

```json
{
  "success": false,
  "message": "MFA challenge has expired."
}
```

## Invalid Challenge

A challenge that does not exist must be rejected.

Expected response:

```json
{
  "success": false,
  "message": "Invalid MFA challenge."
}
```

## Invalid TOTP

An invalid TOTP code must be rejected.

Expected response:

```json
{
  "success": false,
  "message": "Invalid MFA code."
}

```

# Session Creation

An authenticated session is created only after successful MFA
verification.

```text
Email + Password
       ↓
MFA Challenge
       ↓
TOTP Verification
       ↓
Session
       ↓
Access Token
       ↓
Refresh Token

```
The Access Token has a 15-minute lifetime.

The Refresh Token is rotated when the refresh endpoint is used.

---

# Session Revocation

Authenticated sessions can be revoked.

```http
DELETE /auth/sessions/:id
```
